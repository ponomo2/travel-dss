# Данные этапа 2: контракт API и использование

Этап 2 закрыт для демонстрационного MVP согласно уточненному поручению пользователя. Рабочий источник — `data/api/demo_catalog.json`, полный JSON-ответ условного туристического API. Его можно использовать без сети и учетных записей.

## Выбор источника

Проверены [Amadeus Self-Service/test data](https://amadeus4dev.github.io/developer-guides/test-data/), [Amadeus quick start](https://amadeus4dev.github.io/developer-guides/), [Booking Demand sandbox](https://developers.booking.com/demand/docs/getting-started/try-out-the-api), [OpenTripMap](https://dev.opentripmap.org/product). API существуют, однако в проекте нет авторизованного доступа к тарифам и наличию. Тестовые данные Amadeus ограничены и сами по себе не подтверждают предложения по выбранным шести городам. OpenTripMap предоставляет сведения о местах и не заменяет источник пакетов транспорта и проживания. Утверждение об отсутствии туристических API вообще не делается.

Использован разрешенный пользователем вариант: отдельный API fixture. Названия и координаты объектов происходят из реального OSM-каталога; цены, доступность, часы, длительность, классификация и предложения смоделированы. Исходные URL OSM сохранены отдельно в `original_poi_sources`; они не являются источниками выдуманных цен. URL `travel-dss.example` — зарезервированный демонстрационный адрес, запросы к нему не отправляются.

## Состав ответа

| Поле | Содержание |
|---|---|
| schema_version, mode, provider, generated_at, currency, notice | Версия 1.0, явный demo-режим, дата снимка, RUB, пояснение |
| destinations | Шесть городов с координатами и часовыми поясами |
| trip_windows | 22–25 января, 16–19 апреля, 16–19 июля 2027 года |
| pois | 173 объекта: цена, длительность, темы, indoor, человекочитаемые часы, происхождение |
| opening_intervals | Конкретные окна с датой и часовым поясом, временем последнего входа |
| poi_prices_rub | Минимальная, типичная и максимальная цена билета каждого объекта |
| transport_offers | 36 предложений: 2 на каждый город/сезон, туда-обратно, четыре временные точки, терминал, диапазон стоимости |
| stay_offers | 36 предложений: 2 на каждый город/сезон, все ночи, цена за ночь, заезд/выезд, координаты |
| daily_costs | Питание на человека/день, стоимость и время одного трансфера, диапазоны |
| matrices | 6 матриц с объектами, обоими вариантами жилья и терминалом; метры и секунды |

Полный контракт: `data/templates/catalog_api.schema.json`. Генератор: `scripts/build_demo_catalog.py`. Он детерминирован, не зависит от случайного seed и не освежает дату снимка при чтении. SHA256 и размеры набора — `data/api/demo_catalog.metadata.json`; полное покрытие — `reports/data_coverage.json`.

В матрицах пары POI→POI взяты из сохраненного OSRM foot. Связи с фиктивными гостиницами и терминалом смоделированы: геодезическое расстояние ×1.3, скорость 4 km/h. Поэтому весь расширенный набор имеет синтетический статус. `null` означает недостижимость в исходной матрице, а не нулевое время. Перед использованием для реального путешествия потребуются реальные входные точки и маршруты.

Отсутствие окна для объекта в день **внутри** поддерживаемого периода означает закрытие в этом demo-календаре; например, у крытых объектов понедельник выходной. Дата **вне** покрытия не трактуется как закрытие: выбрасывается ошибка отсутствия данных. Строка `opening_hours` используется для объяснения; алгоритм должен использовать типизированные интервалы и `OpeningInterval.fits`.

## Основные функции

```python
from pathlib import Path
from travel_dss.catalog_api import CatalogService, JsonCatalogProvider
from travel_dss.domain import TripRequest

request = TripRequest.model_validate_json(Path('examples/request.json').read_text())
service = CatalogService(
    JsonCatalogProvider(Path('data/api/demo_catalog.json')),
    allow_demo=True,
)
data = service.for_trip(request, 'kazan')

transport = data.transport_offers[0]
stay = data.stay_offers[0]
selected_ids = [poi.id for poi in data.pois[:2]]

cost = data.estimate_cost(transport.quote.id, stay.quote.id, selected_ids)
windows = data.opening_windows(selected_ids[0], data.window.start)
leg = data.travel_between(stay.location.id, selected_ids[0])
```

`for_trip` выбирает только нужный город и точные даты окна, убирает исключенные/закрытые объекты, проверяет обязательные объекты, наличие и срок свежести предложений, границы выезда и возвращения. Неизвестные даты, неподдерживаемый город, отсутствие актуальных предложений и невыполнимые обязательные посещения возвращают понятную ошибку. Проверку полной выполнимости выполняет независимый валидатор `routing.validate_plan` реализованного этапа 5.

`estimate_cost` возвращает сумму дороги туда-обратно, всех ночей, питания за все дни, двух трансферов и билетов выбранных объектов. Дубли посещений и чужие предложения запрещены. `minimum/typical/maximum` — границы и типичная стоимость по предположениям снимка, **не** квантили C10/C50/C90. Сценарные квантили будут рассчитываться на этапе 6.

## JSON, HTTP и SQLite

- `JsonCatalogProvider(path).load()` читает и валидирует снимок.
- `HttpCatalogProvider(url, session=...).load()` получает тот же контракт по HTTPS. В session можно настроить нужную авторизацию. Это адаптер нашего контракта, а не готовый клиент форматов Amadeus или Booking.
- `SqliteCatalogProvider(database).load()` восстанавливает снимок из SQLite.
- `save_snapshot(snapshot, path)` атомарно сохраняет JSON.
- `store_snapshot(snapshot, database)` транзакционно сохраняет снимок и плоские таблицы объектов/котировок.
- `catalog_coverage(snapshot)` проверяет покрытие городов, дат и обязательных данных.

Сбой HTTP/валидации не приводит к скрытой генерации данных. Демонстрационный источник выбирается явно. Поля `synthetic` запрещены в live-каталоге; демонстрационные записи не могут иметь `verified=true` и никогда не дают `POI.confirmed=true`. `Quote.usable` и `POI.usable` допускают их только при `allow_demo=True`.

В demo по умолчанию `as_of=generated_at`, то есть воспроизводится состояние условного API на указанную дату. Этот момент виден в результате. Переданный `as_of` проверяется как обычно: через 25 часов котировка с TTL 24 часа уже не принимается. В live по умолчанию используется текущее UTC-время. Никаких изменений `observed_at` ради прохождения TTL нет.

## Команды

```bash
make demo-data
.venv/bin/travel-dss sync-catalog --allow-demo
.venv/bin/travel-dss catalog kazan --allow-demo --output reports/demo_trip_data.json
.venv/bin/travel-dss catalog kazan --allow-demo --as-of 2026-11-13T12:00:00+03:00
```

Последняя команда демонстрирует отказ для просроченных предложений. `sync-catalog` сохраняет демонстрационную базу `data/processed/catalog_demo.sqlite`, отдельно от исходного OSM-каталога `catalog.sqlite`; рядом сохраняет отчет покрытия. Для внешнего API вместо файла: `--url https://your-provider.example/catalog` с телом по общей схеме.

Результат примера Казани на 16–19 апреля: минимальная по типичной стоимости базовая комплектация 32 350 ₽, диапазон 26 237.50–41 100 ₽; без входных билетов. Остаток от бюджета 45 000 ₽ — 12 650 ₽ по типичной оценке. Это объяснение стоимости набора услуг, а не готовая рекомендация маршрута.
